# ライブラリ一覧 設計メモ (2026-11)

- 位置づけ: デスクトップの中央ペイン (曲の一覧 / カード表示 / アルバム / アーティスト) の
  **スクロールとデータ取得** の仕様。`docs/ui-spec.md` とユーザーガイドはこのメモと矛盾してはならない。
- 経緯: v0.21.0 までは 500 件ずつ取得し、末尾に近づくと追加取得していた。スクロールできる範囲が
  「読み込み済みの行」だけなので、スクロールバーを下まで引くと追加取得 → 内容が伸びる →
  つまみが上へ戻る、を繰り返し、数万曲のライブラリでは一番下へ行けなかった。
  **この仕様 (末尾での追加取得) は廃止した (仕様変更)。**

## 1. モデル

- **スクロール範囲は最初から全件ぶん。** 一覧を開いたらまず件数を取り、行数 (グリッドは
  `ceil(件数 / 列数)` 行) をその件数で確保する。スクロールバーのつまみの大きさは読み込みで変わらず、
  一番下まで引くと本当の最後の項目に着く。
- **データは見えている範囲だけ取る (ウィンドウ取得)。** 一覧を固定長のページ (200 件) に区切り、
  表示範囲と重なるページ + 前後 1 ページを取得する。
- **未取得の行はプレースホルダ。** 高さは実データの行・カードと同じで、取得後に位置がずれない。
- **全件はメモリに載せない** (`docs/ui-spec.md` 1.4)。ページキャッシュは LRU で 20 ページまで
  (表示中のページは捨てない)。全件ぶん持つのは件数と、必要になったときの track_id の列だけ。

対象は TrackTable (ライブラリ / プレイリスト / スマートプレイリスト / 検索・絞り込み)、
TracksView (カード表示)、AlbumsView、ArtistsView。Inbox と「最近再生した曲」は件数に上限のある
メモリ上の一覧で、同じ仕組みに配列を流す (件数 = 配列の長さ)。

## 2. 取得の規則

- 一覧の同一性は **キー** (スコープ・検索語・絞り込みタグ・並び順) で決まる。キーが変わったら
  先頭へ戻し、先頭のページをすぐ取る。
- キーのうち並び順を除いた部分を **グループ** (スコープ・検索語・絞り込みタグ) と呼ぶ。件数と
  「どの項目が入っているか」はグループで決まる。**並び順だけを変えたとき** (グループは同じ) は
  件数を取り直さず、行数を保ったまま、先頭のページを古い並びで表示し続けて、新しい並びが届いたら
  入れ替える (一度 0 行にして空白を見せない)。グループが変わったらキャッシュを全部捨てる。
- **取り直し (リビジョン)**: ライブラリが変わったとき (編集・取り込み・削除など) はキーを変えずに
  件数と表示中のページを取り直す。スクロール位置は保ち、取り直しが届くまで古い行を表示し続ける
  (プレースホルダに戻さない)。表示範囲外のキャッシュは捨てる。
- **古い応答は捨てる。** キー・リビジョンが変わるたびに世代番号を進め、世代の違う応答は使わない。
- **同じページを二重に取らない。** 取得中のページは世代ごとに覚えておく。
- **スクロールバーを引いているあいだ、通過したページを取らない。** 表示中のページが手元にあり
  (キャッシュ済み)、直前の表示範囲からの移動が 1/4 ページ未満なら、足りないのは先読みぶんだけ =
  普通のスクロールなので、すぐ取る。それ以外 (先読みを追い越した・1 回で大きく動いた =
  スクロールバーのドラッグや離れた位置へのジャンプ) は、100 ms スクロールが止まってから、
  そのとき見えている範囲を取る。
  一覧を開いた直後と取り直しは待たずに取る。
- **件数とページは別々に届く。** 届いたページを「いまの件数」で切り詰めない (取り直しで件数が
  増えたとき、ページが件数より先に届くと、増えたぶんの末尾が未取得のまま残ってしまう)。
  件数の外の行は読むときに隠す。件数が減ったら範囲外を捨て、件数だけが増えたら、短くなっている
  最後のページを取り直す。
- **取得の失敗**: 400 ms・1.2 秒待って 2 回まで自動で取り直す (DB のロックなど一時的な失敗は見せない)。
  それでも取れなかったページは「失敗」として覚え、自動では取り直さない。表示範囲に失敗したページが
  あるあいだ、一覧の下端に「一覧の一部を取得できませんでした。クリックして再試行」を出す
  (展開行の取得失敗と同じ部品)。失敗の記録は、再試行・キーの変更・取り直しで消える。

## 3. API (Tauri コマンド)

件数・ID 列は、ページ取得と **同じ WHERE 句の組み立て** を通す (件数とページが食い違わないこと)。

| 一覧 | ページ | 件数 | ID 列 (表示順) |
|---|---|---|---|
| ライブラリ / 検索 | `get_tracks` / `search_tracks` | `count_tracks(query?)` | `get_track_ids(query?, sortField, sortOrder)` |
| プレイリスト (スマート含む) | `get_playlist_tracks` / `get_smart_playlist_tracks` | `count_playlist_tracks(playlistId, query?)` | `get_playlist_track_ids(playlistId, query?, sortField, sortOrder)` |
| アルバム | `get_albums(…, query?, playlistId?)` | `count_albums(query?, playlistId?)` | — |
| アルバムの曲 | `get_album_tracks(albumKey, query?, playlistId?)` | — | — |
| アーティスト | `get_artists(…, query?)` | `count_artists(query?)` | — |

- Rust 側の単一の組み立て: ライブラリ / 検索は `Database::search_where`、通常プレイリストは
  `static_playlist_filter`、スマートプレイリストは `smart_playlist_ordered_ids` (評価 → 並べ替え →
  検索の積)、アルバムは `album_scope_where`。ページ・件数・ID 列はそれぞれ同じ関数を使う。
- **並びは必ず一意にする。** 列で並べたときは最後に `track_id`、既定の並び (曲名) も `track_id`、
  プレイリストの手動順は `sort_index` → `rowid` で決める。同値の行の相対順が決まらないと、
  ページと ID 列で並びが食い違う。
- **アルバム表示はどのスコープでもサーバ集約。** プレイリスト / 検索のときは、その範囲の曲だけで
  アルバムを束ね (曲数・カバー・合計時間もその範囲の曲で数える)、展開したときの曲もその範囲の曲だけ。
  プレイリストに同じ曲が複数回入っていても 1 曲として数える。
- 契約はテストで固定する: 「件数 == 全ページを連結した長さ」「ID 列 == 全ページを連結した track_id の列」
  (`src-tauri/src/db/windowed_list_tests.rs`。ジャンルの完全一致・プレイリスト・スマートプレイリスト・
  並びのキーが同値の行を含む)。

### 3.1 曲の一覧のページは「ID 先行」+ ID 列のキャッシュ

曲の一覧 (ライブラリ / 検索 / プレイリスト / スマートプレイリスト) のページは、次の 2 段で取る。

1. その一覧の **表示順の track_id 列** を作る (`SELECT track_id … ORDER BY …`。スマートプレイリストは
   評価 → 並べ替え)。並べ替えるのは (並びのキー, track_id) だけで、全列は運ばない。
2. その列から 1 ページぶんを切り出し、行を ID で引く (`get_tracks_by_ids`)。

1 の ID 列は **プロセス内に覚えておき** (`src-tauri/src/db/list_cache.rs`)、件数 (スマートのみ)・
各ページ・ID 列・アルバムの範囲指定で使い回す。並べ替え (NATSORT) とスマートプレイリストの評価は
ライブラリ全体を走査するので、呼び出しごとにやり直すと 1 ページ取るたびに全件ぶんのコストがかかる。

- 無効化: どのコネクションでも書き込みトランザクションがコミットされるたびに捨てる
  (`Database::open` が commit hook を張る。読み取りでは呼ばれない)。DB ファイルを差し替える復元も捨てる。
- commit hook はコミットの直前に呼ばれるので、コミットから 250 ms 以内に計算した結果は覚えない。
- 時間で結果が変わる条件があるので、60 秒を過ぎたエントリも使わない。覚えるのは 8 一覧まで
  (1 件あたり最大「曲数 × 8 バイト」)。

計測 (37,082 曲の生成 DB、release ビルド、200 件 1 ページ。
`cargo test --release windowed_list_bench -- --ignored --nocapture`):

| ページ | v0.21.0 までの SQL (全列を並べ替え) | ID 先行・一覧を開いた最初の 1 回 | ID 先行・2 ページ目以降 |
|---|---|---|---|
| 曲名順 offset 0 | 9.8 ms | 51.3 ms | 0.9 ms |
| 曲名順 offset 36,800 | 157.4 ms | 47.8 ms | 1.0 ms |
| アーティスト順 offset 36,800 | 205.4 ms | 60.0 ms | 0.9 ms |

最初の 1 回は LIMIT つきの並べ替えではなく全件の ID 列を作るので、先頭のページだけを見れば
以前より遅い (約 10 ms → 50 ms)。その代わり、どの位置のページもその後は約 1 ms で、全選択・
範囲選択・再生で使う ID 列も同じ列をそのまま返す。

### 3.2 複数曲の操作は 1 回の呼び出し

全選択は数万曲になる。trackId だけで済む操作は、曲数ぶん IPC を往復させず 1 回で渡す。

| 操作 | コマンド |
|---|---|
| キューに追加 | `enqueue_tracks(trackIds)` (渡した順で末尾へ。通知は 1 回) |
| 次に再生 | `enqueue_tracks_next(trackIds)` (現在曲の直後に、渡した順で並ぶ) |
| レーティング | `set_tracks_rating(trackIds, rating)` (1 トランザクション。失敗したらどの曲も変わらない) |
| 削除の確認 | `preview_delete_tracks(trackIds, root?)` → 件数・先頭の 5 曲・ルート外のファイル数 |
| 削除 / プレイリストへ追加・から外す / ジャンルタグ / 解析 / 変換 | 以前から ID 列を 1 回で渡している |

曲の情報そのものが要る操作 (**Get Info の一括編集**・**Crate への追加**。`Ctrl+I` / `Ctrl+Shift+C` を含む)
は選択した曲を読み込むことになるので、**1,000 曲まで** にする (`src/lib/selectionLimit.ts`)。
超えているときは何もせず、理由をトーストで知らせる (ライブラリ全体をメモリに載せない)。

## 4. フロントエンドの構成

- `src/lib/windowedList.ts` — React に依存しない本体。純関数 (ページ計算・取得タイミングの判定・
  カーソル移動の行番号計算)、`PageCache` (LRU)、`WindowLoader` (世代管理・重複排除・スクロール停止待ち・
  失敗の再試行・先行表示の並べ替え)。`tests/desktop/windowedList.test.ts` で固定。
- `src/hooks/useWindowedList.ts` — `useWindowedList({ key, group, revision, count, fetchPage })`。
  **一覧のキー・件数・見えている範囲のページをまとめて持つ唯一の入口** で、4 つのビューが共用する。
  件数は数値 (メモリ上の一覧) か取得関数 (サーバの一覧) を渡す。件数の取得は `useListCount`
  (グループが変わったら未確定に戻し、取り直しでは前の件数を保つ)。
  `WindowLoader.sync` はレンダー中に呼ぶ (前の一覧の行を新しいキーで描かないため)。そのため sync は
  「同じ引数なら何度呼んでも同じ状態」で、取得などの副作用を持たない (取得は effect の `schedule`)。
- `src/lib/trackListQuery.ts` — ストアの状態から「どの一覧か」(`TrackListQuery`) とキー・グループを
  決める純関数 (`tests/desktop/trackListQuery.test.ts`)。`src/api/trackList.ts` が各コマンドへ振り分ける。
- `src/hooks/useTrackList.ts` — 曲の一覧 (TrackTable / TracksView) 用の薄い配線。ID 列の遅延取得
  (`getIds`)、選択中の曲の解決 (`resolveTracks`)、表示順への並べ直し (`orderByList`)、並べ替えの
  先行表示 (`applyOrder`)。`useTrackListCount` は件数だけを同じ条件で取る (ツールバー用)。
- TrackTable は描画と行・メニューの配線だけを持ち、振る舞いは hook に分ける:
  `useTrackSelection` (選択・カーソル)、`usePlaylistReorder` (手動並べ替え・行のドラッグ)、
  `useTrackListKeys` (キーボード。受けるイベントの判定は `src/lib/listKeys.ts`、
  `tests/desktop/listKeys.test.ts`)、`useTrackColumns` (列ヘッダのリサイズ・並べ替え)。
  セルの表示は `components/TrackFieldCell.tsx`。
- `src/lib/gridRows.ts` `gridLayout` — 件数と列数からグリッドの行を決める。展開行は
  「読み込み済みで、展開中の項目」の行の直後に 1 行だけ差し込む。行キーは展開の開閉で変わらない
  (`tests/desktop/gridRows.test.ts`)。
- AlbumsView / ArtistsView が共有するもの: `useGridExpansion` (展開中の項目と、取り直し後の位置合わせ)、
  `useKeyedCache` + `src/lib/keyedCache.ts` (展開行の遅延取得キャッシュ。一覧が切り替わったら捨て、
  ライブラリが変わったら「次に使うとき取り直す」。切り替え前に始めた取得の結果は覚えない。
  `tests/desktop/keyedCache.test.ts`)。
- 未取得の行・カードは同じ高さのプレースホルダ (`.cb-row.ph` / `PlaceholderCard`)。カード下のラベル行は
  CSS で高さを固定し、行の高さの見積もりと実測を一致させる (スクロール範囲が実測で伸び縮みしない)。
- ストアの `tracks` は **メモリ上の一覧 (Inbox / 最近再生した曲) 専用**。ライブラリ・プレイリスト・
  検索では空。ライブラリ変更の通知は `libraryRevision`。件数はストアに置かず、各ビューと
  ツールバーがそれぞれ同じ条件で取る。
- 一覧に読み込まれているとは限らない曲 (再生中の曲など) は ID で取り直す (`get_tracks_by_ids`)。

## 5. 操作 (読み込んでいない行をまたいでも同じ結果になること)

選択は **track_id の集合** で持ち、範囲選択の起点とカーソルは **行番号 + track_id** で持つ。
行番号から track_id が要るとき、読み込み済みならキャッシュから、無ければそのページ (1 行の移動) か
一覧の全 ID 列 (範囲・全選択・再生) を取る。

| 操作 | 方法 |
|---|---|
| クリック / Ctrl・Cmd クリック | 行の track_id を選択に出し入れ |
| Shift クリック / Shift+カーソルキー | 起点〜対象の行番号の範囲を ID 列から切り出す |
| Ctrl・Cmd+A | ID 列の全件 |
| ↑ ↓ / PageUp PageDown / Home End | 行番号を動かし、その行へスクロール。移動先の曲はそのページだけ取って調べる |
| ダブルクリック / Enter / メニューの再生 | ID 列の全件をキューに入れ、その行から再生 |
| 行のドラッグ | 選択中の track_id を表示順で渡す (下記) |
| 右クリックの操作 | 選択中の track_id に 1 回の呼び出しで適用 (§3.2)。Get Info・Crate は 1,000 曲まで |
| 並び順の変更 | キーが変わる (グループは同じ) → 先頭へ戻る。行数・選択は保つ |
| 検索・スコープの変更 | グループが変わる → 先頭へ戻る。選択は解除 |
| ライブラリの変更 | リビジョン → スクロール位置を保って取り直す。選択は保ち、一覧から消えた曲だけ外す |

- **選択**: 見ている一覧 (グループ) が変わったら解除する。並び順の変更・一覧の取り直しでは残す
  (v0.21.0 までは取り直すたびに全解除していた)。取り直しのあと、ID 列と突き合わせて一覧から消えた曲を
  選択から外す。
- **キーボードを受ける条件** (`isListKeyEvent`): モーダルが開いているとき、入力欄・セレクト・編集中の
  要素にフォーカスがあるときは受けない。PageUp / PageDown / Home / End は、ほかの場所ではその場所の
  スクロールに使うキーなので、フォーカスがどこにも無いか一覧の中にあるとき、またはポインタが一覧の上に
  あるときだけ受ける。↑ ↓・Ctrl+A・Enter・Delete は従来どおり (上の除外に当たらなければ受ける)。
- **行のドラッグの順序**: 選択が複数になった時点で ID 列を先に取っておき、ドラッグ開始 (同期処理) で
  表示順に並べる。ID 列がまだ届いていないあいだに掴んだ場合だけ、読み込み済みの行の順 → 残りは
  選択した順になる。
- **プレイリストの手動並べ替え** (行のドラッグ / Alt+↑↓。`usePlaylistReorder`):
  操作のたびに画面の並びを先に入れ替え (取得済みの行を並べ替えるだけ。スクロールもその並びでの位置へ)、
  最後の操作から 300 ms 待って 1 回で書き込む (連続操作をまとめる)。書き込みは全曲順での全置換なので、
  直前に DB の全曲順を取り直し、操作を始めたときと違っていたら (別の場所で曲が足された・外された)
  書き込まずにエラーを出して取り直す。別のプレイリストへ移る・画面を離れるときは待たずに書き込む。
  読み込んでいない行にかかる移動は、その行だけ書き込みのあとの取り直しで正しい並びになる。

## 6. グリッドの展開行

- 展開できるのは読み込み済みのカードだけ (プレースホルダはクリックできない)。
- 展開中の項目は「項目キー + 開いたときの通し番号」で覚え、展開行を描くための項目そのものも持つ
  (`useGridExpansion`)。取り直しで位置がずれたら、読み込み済みの項目から同じキーを探し直す。
  見つからなければ閉じる。一覧が切り替わったら閉じる。
- アーティストの中で開いているアルバムは「どのアーティストの中で開いたか」と一緒に覚え、展開が
  閉じたら (取り直しで閉じた場合も) 無効にする。
- 行キー: グリッド行 `g:<列数>:<行番号>`、展開行 `x:<項目キー>`。展開の開閉で実測キャッシュを捨てない
  (`docs/refactor/design.md` の規則のまま)。
